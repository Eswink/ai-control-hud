# Discovery report version contract

Status: H12 compatibility policy for `tools.discovery`

The metadata-only discovery tool writes a JSON report with an explicit top-level `reportVersion`. Consumers must validate this value before interpreting any fields.

The current generator version is:

```text
reportVersion = 2
```

Supported consumer versions are explicitly enumerated in `tools.discovery_report`:

```text
1, 2
```

Unknown future versions are rejected. Consumers must never infer a schema from whichever fields happen to be present.

## Strict loader

Use:

```python
from tools.discovery_report import load_report

loaded = load_report(".local/discovery-report.json")
print(loaded.source_version)
report = loaded.data
```

Or validate from the command line:

```bash
python -m tools.discovery_report .local/discovery-report.json
```

Accepted input prints its source/current versions and exits 0. Invalid or unsupported input exits 2.

The loader distinguishes:

- `InvalidDiscoveryReport` — missing/non-integer version, malformed JSON, unreadable file, or non-object root;
- `UnsupportedDiscoveryReportVersion` — structurally versioned report whose version is not explicitly supported.

Python `bool` is deliberately rejected as a version even though `bool` subclasses `int` in Python.

## Version history

### v1

The original privacy-safe discovery report contained:

- generated timestamp and platform metadata;
- metadata-only ZCode CLI/root/SQLite schema discovery;
- metadata-only CommandCode CLI/root/JSON-shape discovery;
- privacy flags proving no network calls, SQLite row reads, JSON values, hostname, or username were included.

The v1 generator did not have the later optional aggregate probes.

### v2

v2 preserves the original core top-level `platform`, `zcode`, and `commandCode` structure and adds/refines optional operational evidence:

- explicit distinction between discovery-script network behavior and optional CommandCode CLI status probing;
- CommandCode environment-variable **presence only**, never values;
- optional CommandCode status JSON-shape probe;
- optional aggregate ZCode task status/timestamp-magnitude summary;
- explicit privacy flags for SQLite content fields, environment values, and CommandCode status values;
- Windows `cmdc` CommandCode CLI alias support.

The v2 additions are metadata-only and keep the original privacy boundary.

## v1 compatibility normalization

`tools.discovery_report.normalize_report()` accepts v1 and returns a copy with safe v2-era optional defaults so a modern consumer can use one metadata view without guessing:

- legacy `privacy.networkCalls` becomes `privacy.networkCallsByDiscoveryScript`;
- `commandCodeCliMayUseNetwork = false`;
- `sqliteContentFieldsRead = false`;
- `environmentValuesIncluded = false`;
- `commandCodeStatusValuesIncluded = false`;
- `zcode.taskValueSummary = null`;
- `commandCode.environment = {}`;
- `commandCode.statusProbe = null`.

The original source `reportVersion` remains `1`; normalization does not pretend old evidence was generated by v2.

The input mapping is deep-copied and is never mutated in place.

## Future versions

A future `reportVersion = 3` must not be accepted merely by changing the generator constant. A version bump requires all of the following in the same iteration:

1. document the incompatible/meaningful schema changes;
2. decide whether older versions remain supported;
3. add an explicit normalization/migration path if compatibility is safe;
4. add the new version to `SUPPORTED_DISCOVERY_REPORT_VERSIONS`;
5. add regression tests for old/current/future-version rejection;
6. keep privacy guarantees at least as strict as the previous version.

A CI test asserts that `tools.discovery.REPORT_VERSION` equals `CURRENT_DISCOVERY_REPORT_VERSION`, so a generator-only bump fails rather than silently making consumers accept or misread a new format.

## Separate provider-discovery report

`tools.provider_discovery` also emits a versioned JSON document, but it is a different report contract with different fields and privacy semantics. Do not load it with `tools.discovery_report` merely because its current numeric `reportVersion` is also `2`.

If provider-discovery needs cross-version consumption, it should receive its own explicit loader/version policy rather than overloading the general discovery schema.

## Privacy invariants

Version compatibility never relaxes the discovery privacy boundary. Reports must continue to omit secret values, prompt/task content, username/hostname, and raw database row content unless a future version explicitly changes the product contract and receives separate review.
